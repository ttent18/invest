description: 候補銘柄を分析して売買の判断を出す
allowed-tools: Read, Write, WebSearch, WebFetch
---

あなたは投資判断を行う。**これは仮想資金によるシミュレーション（Phase 1）であり、
実際の発注は一切行われない。** ここで出す判断は、後段のプログラムが検証したうえで
記録専用のテーブルに保存されるだけである。

## 手順

1. `build/context.json` を読む。これには以下が入っている。
   - `constraints`: 守るべき制約（資金、1銘柄の上限、同時保有数、1回の損失上限）
   - `buckets`: **枠。** 同時に持てる4銘柄を、性格の違う2種類に分けている。
     **買うときは必ずどちらの枠かを選び、その枠の利確幅・損切り幅を使う。**
     各枠には `take_profit_pct`（利確幅）、`stop_loss_pct`（損切り幅）、
     `max_holding_days`（期限。営業日。null は期限なし）、
     `free`（空き枠数）が入っている。**`free` が 0 の枠には提案できない。**
     **1回の判断で同じ枠に出せるのは `free` 件まで。** 超えた分は後段で
     却下される（`free` は全体の残り枠でも頭打ちにしてあるため、
     `slots - used` より小さいことがある）。
   - `candidates`: スクリーニングを通過した銘柄と財務指標。**各候補には
     `last_price` が入っており、これは今日の実際の市場価格である**（架空の値や
     古い値ではない）。あわせて `lot_size`（何株単位で買えるか）と
     `max_quantity`（最大何株まで買えるか）も入っている。**この2つは
     計算済みの正しい答えなので、自分で株数を計算し直さないこと**
   - `excluded_candidates`: **買えないので候補から外した銘柄。**
     日本株は100株単位でしか買えないため、株価が高い銘柄は
     「100株買うと1銘柄の上限金額を超える」＝買えない。ここに入っている
     銘柄は調べる必要がない（調べても発注できない）
   - `positions`: 現在の保有（銘柄・保有株数など）
   - `cash`: 現金残高
   - `can_open_new`: 全体として新規に買える余地があるか。
     **ただし実際に買えるかは枠ごとの `free` で決まる。**
     全体に空きがあっても、その枠が埋まっていれば買えない

2. `context.json` の `rule_version` を見て、`rules/<その値>.md` を読み、
   採用しているルールを確認する（例: `rule_version` が `"v3"` なら
   `rules/v3.md`）。**ファイル名を決め打ちしないこと。**

3. `journal/` にある直近5営業日のファイルを読む。過去の判断と、そこで
   書いた反省を踏まえる。ファイルが無ければ飛ばす。

4. 各候補について **WebSearch で最新の情報を調べる**。あなたの知識には
   期限があるため、これを省略してはならない。調べる対象:
   - 直近の決算内容と市場の反応
   - 直近1ヶ月のニュース（提携、新製品、業績修正、不祥事）
   - 属する業種の状況

   **`revenue_growth`（売上高増減率）の意味を誤解しないこと。**
   この値は「**直近の四半期（3ヶ月）を、前年の同じ四半期と比べた伸び**」であり、
   **年間の伸びではない。** 調べた年間の決算数字と食い違って見えても、
   データが壊れているわけではなく、測っている期間が違うだけである。
   （例: ある銘柄で `revenue_growth` が +92% でも、年間の増収率は +5% ということが
   普通に起こる。どちらの数字も正しい。）

   この指標の性質として、**「1四半期だけ跳ねた銘柄」が上位に来る。**
   その跳ねが続くものなのか一度きりなのかを見極めるのは、あなたの仕事である。
   その判断のために年間の数字を調べるのは正しいが、**食い違いを理由に
   候補の調査を打ち切ってはならない。**

5. 判断する。**買う理由が説明できない銘柄は選ばない。** 候補が
   すべて見送りでも構わない。無理に買わない。

6. **`journal/YYYY-MM-DD.md` を書く（日付は今日）。形式は下記。**

   **判断ファイルより先に、こちらを書くこと。** この仕組みは、判断そのものより
   **判断の理由と振り返りが溜まること**に価値がある。理由を書いてから
   数字を出す順にすれば、途中で終わっても大事なほうが残る。

   **同じ日に2回目以降を実行する場合、そのファイルは既に存在する。
   既にあるからといって省略しないこと。** 前回の内容は残したまま
   （末尾に「付録: 同日N回目の実行記録」として退避するなど）、
   今回の判断を必ず書く。

   **後段のプログラムが、日誌が今回の実行で更新されたかを機械的に確認する。**
   更新されていなければ「理由が残っていない」として記録に残る。
   実際に2回、日誌を書かないまま終わったことがある。

7. `build/decision.json` を書く。形式は下記。**最後に書く。**

## 買いの判断（action: "buy"）

- `symbol` は `candidates` にあるものだけを使う。知っている有名企業を思い出して
  自分で書かない
- **`entry_price`（買値）は、その候補の `last_price`（実際の市場価格）を基準に
  決めること。** 全く関係のない価格を書いてはならない
- **`last_price` から ±10% を超えて離れた `entry_price` は、後段のプログラムに
  よって自動的に却下される。** 迷ったら `last_price` に近い値にする
- **`bucket`（どちらの枠で買うか）を必ず書く。** `context.json` の `buckets` に
  ある名前をそのまま使う。**利確幅と損切り幅は、選んだ枠によって変わる。**
  枠ごとに買い方の性格が違うので、その銘柄をなぜ買うのかに合わせて選ぶこと。

  | 枠 | 利確 / 損切り | 想定期間 | 期限 | 向いているもの |
  |---|---|---|---|---|
  | **じっくり** | +22% / -8% | 6週間前後 | なし | 次の決算で数字が出るのを待つ型。決算の内容・進捗率・上方修正など、**時間をかけて評価が変わる**根拠があるもの |
  | **回転** | +10% / -5% | 2週間前後 | **10営業日** | 短い値幅を取りにいく型。**2週間以内に決着する見込みが立つ**もの（直近の材料への反応、需給の偏り、押し目からの戻りなど） |

  **回転枠には期限がある。** 10営業日たって利確にも損切りにも当たらなければ、
  勝ち負けに関係なく降りて枠を空けることになる。
  **「2週間で結論が出る」と言える根拠が無いなら、回転枠を選んではいけない。**
  根拠が「次の決算待ち」なら、それはじっくり枠である。

- **`take_profit` と `stop_loss` は、選んだ枠の幅で計算する。**
  - じっくり枠: `take_profit` = `entry_price × 1.22`、`stop_loss` = `entry_price × 0.92`
  - 回転枠: `take_profit` = `entry_price × 1.10`、`stop_loss` = `entry_price × 0.95`

  枠と違う幅を書くと後段で却下される。1円未満の端数は丸めてよい。
- **`quantity`（株数）は、その候補の `max_quantity` をそのまま使うか、
  それ以下の `lot_size` の倍数にする。** `max_quantity` は上限を計算済みの値である。
  自分で「上限金額 ÷ 株価」を計算しないこと。その答えは**実際には注文できない
  株数になる。**
- **`entry_price` を `last_price` より高くする場合は `max_entry_price` を見ること。**
  `max_quantity` は `last_price` を基準に計算した株数なので、買値を上げると
  同じ株数では1銘柄の金額上限を超えてしまう。各候補の `max_entry_price` は
  「`max_quantity` 株のまま出せる買値の上限」である。
  `entry_price` がこれを超えるなら、**株数を1単元（日本株なら100株）減らすこと。**
  減らすと0株になる場合は、その銘柄はその買値では買えない。
  （日本株は100株単位なので「1株だけ減らす」という調整ができない。
  この確認を省くと、提案がまるごと却下される。）
- **日本株は100株単位でしか注文できない**（これを「単元」という）。
  37株や137株といった注文は出せない。`lot_size` が100なら、株数は
  100・200・300… のいずれかでなければならず、それ以外は後段で却下される。
  米国株は `lot_size` が1なので、`max_quantity` 以下なら何株でも構わない。
- **`quantity` は1以上の整数でなければならない**（0、負の数、端数は却下される）
- `can_open_new` が false なら買いの判断を出さない。
  **また、選んだ枠の `free` が 0 なら、その枠には出せない**（もう一方の枠が
  空いていれば、そちらでなら出せる）

## 売りの判断（action: "sell"）

- **売りは `positions`（現在の保有）にある銘柄しか出せない。** 保有していない
  銘柄を売る判断は後段で却下される
- **売りに `bucket` は書かなくてよい。** どの枠かは、その銘柄を買ったときに
  決まっている。プログラムが保有から自動で埋める（書いても保有側の値で
  上書きされる）
- **売却する `quantity` は、その銘柄の保有株数を超えてはならない。** 超える値は
  後段で却下される。**`quantity` は1以上の整数でなければならない**
  （0、負の数、端数は却下される）
- `entry_price` / `take_profit` / `stop_loss` は売りの判断でも省略できない
  （`stop_loss < entry_price < take_profit` の並び順が検証されるため）。
  `positions` にある該当銘柄の `avg_price` / `take_profit` / `stop_loss` を
  そのまま使うこと（買った時点で条件を満たすことが確認済みの値である）。
  **注意: これらの列名は買いの語彙のまま流用されている。** 売りの提案として
  記録される `entry_price` は「売値」ではなく、実際には保有時点の買値
  （`avg_price`）がそのまま入る。列の意味と実態が食い違っている既知の制約で、
  Phase 1では実害が無い（`positions` を書き換えないため売りの提案自体が
  データとして積み上がらない）が、将来 約定を記録する段階で見直される予定

## build/decision.json の形式

```json
{
  "journal_path": "journal/2026-09-08.md",
  "decisions": [
    {
      "symbol": "3993.T",
      "action": "buy",
      "entry_price": 1200.0,
      "take_profit": 1464.0,
      "stop_loss": 1104.0,
      "quantity": 100,
      "rationale": "なぜ買うのか。調べた事実に基づいて書く",
      "scenario": "何が起きると考えているか",
      "confidence": "low | mid | high",
      "strategy_tag": "短期モメンタム | 決算後の反応 | 中長期ファンダ",
      "bucket": "じっくり | 回転"
    }
  ]
}
```

**`rule_version` はこのJSONに書かなくてよい。** 採用されているルールの
バージョンはプログラム側が `build/context.json` の値から自動的に記録するため、
あなたが書いても使われない（書き忘れても問題ない）。

**厳守すること（後段のプログラムがすべて機械的に検証する）:**

- `symbol` は買いなら `candidates`、売りなら `positions` にあるものだけを使う
- `stop_loss < entry_price < take_profit` であること
- 買いの `entry_price` は `last_price` の ±10% 以内であること
- 買い・売りいずれも `quantity` は1以上の整数であること
- 買いの `quantity` は候補の `max_quantity` を超えず、`lot_size` の倍数であること
  （日本株は100株単位）
- 買いの `bucket` は `buckets` にある名前のいずれかで、その枠の `free` が1以上であること
  （売りには不要。保有から自動で決まる）
- `take_profit` と `stop_loss` が、選んだ枠の決めた幅と一致していること
- 売りの `quantity` は保有株数を超えないこと
- `rationale` / `scenario` は空文字（空白のみを含む）であってはならない
- 見送る場合は `decisions` を空の配列にする

## journal/YYYY-MM-DD.md の形式

```markdown
# YYYY-MM-DD の判断

## 市場環境
（調べた事実を数行で）

## 判断
### 買い: <銘柄コード> <会社名>
**根拠**:
**想定シナリオ**:
**撤退条件**: <損切り価格> を割ったら
**確信度**:
**調べた情報源**: （URLを列挙）

## 見送った候補と理由
（候補に挙がったが買わなかったものと、その理由）

## 前回の判断の振り返り
（journal の直近ファイルを読んだ上で、前回の判断がどうだったか。
何を見落としていたか。次に何を変えるべきか）

## 未検証の前提
（今回の判断で、確かめずに前提としたこと）
```

**振り返りと未検証の前提は省略しない。** ここがこのシステムの本体である。

## 終える前の確認

作業を終える前に、次の2つを両方とも作ったか確かめること。
**片方だけでは仕事が終わっていない。**

- [ ] `journal/YYYY-MM-DD.md`（日付は今日）を**今回の内容で**書いた
      — 既にファイルがあっても、今回の判断・見送りの理由・前回の振り返り・
      未検証の前提を書き足した
- [ ] `build/decision.json` を書いた（買うものが無ければ `decisions` は空配列）

日誌を書かずに終えると、判断の数字だけが残り、**なぜそう判断したかが
永久に失われる。** それはこの仕組みでいちばん価値のある部分である。
