# AI投資支援システム 設計書

作成日: 2026-09-07 / 最終更新: 2026-09-07（全面改訂）

**利用者は投資初心者である。用語は付録Aを参照。設計・実装・画面表示のいずれでも投資用語を説明なしに使わないこと。**

## 1. 背景と目的

SBI証券口座を持つ投資初心者が、AIと共に学びながら投資を行うためのシステム。

**目的は利益を得ること。** そのための手段として、判断とその根拠を記録し、
ベンチマークと比較し、振り返る。何が効いて何が効かないかを測定しなければ
「儲かる可能性が高い方」を選ぶこと自体ができないため、測定機構を中核に置く。

### 明確にしておくこと

本システムは利益を保証しない。参考にした動画の発信者自身も
「100%利益が出るわけではない」「基本的には長期のインデックス投資のほうが
パフォーマンスが良いというデータが出ている」と述べており、発信者自身は
インデックス投資家である。ベンチマーク比較を必須とするのはこのためであり、
**自分の手法がインデックスに勝てていないと判明した場合、それは有効な発見**
として扱う。

### 目標（2026-09-07 設定）

**55万円 → 100万円（+81.8%）**

期限は**仮に1年**と置く。根拠のある期限は実測値が出てから確定する（11.2 / 16.2）。

| 期間 | 必要な年率 |
|---|---|
| 4ヶ月 | +501%（不可能） |
| 1年 | +81.8% |
| 2年 | +34.8% |
| 3年 | +22.0% |
| 4年 | +16.1% |

複利の回転を前提とすると、到達時期は**勝率**で決まる。

前提: -8%損切り / +22%利確、同時5銘柄、1銘柄=資金の20%、平均2週間で回転（年125トレード）

| 勝率 | 1トレード期待値 | 年率 | 到達時期 |
|---|---|---|---|
| 45% | +5.5% | +293% | 約5ヶ月 |
| 40% | +4.0% | +170% | 約7ヶ月 |
| 35% | +2.5% | +86% | 約1年 |
| 30% | +1.0% | +28% | 約2.4年 |
| **27%** | **±0%** | 横ばい | **到達しない** |

**この試算は1銘柄=資金20%のフル稼働を前提とした上限側の見積もりである。**
実測の勝率が出るまでは10〜15%で運用するため、初期の到達ペースはこれより遅い
（17章 未解決の論点を参照）。

**分かれ目は勝率27%。** 4回に1回強勝てばよい。O'Neilが損切りを浅く・利確を深く設計したのは、
低い勝率でも生き残れるようにするためである。

### 非目標

- 完全自動売買（発注は常に手動）
- デイトレード
- 常時稼働の株価監視
- 他人が使えるプロダクトにすること

## 3. 中核となる設計判断

### 3.1 株価の監視は自作せず、SBIの逆指値・OCO注文に委譲する

当初は15分ごとのポーリング監視を設計していたが、**廃止した**。

- yfinanceは20分遅延であり、遅延データで損切りを検知しても執行が間に合わない
- 手動発注が挟まるため、条件到達から約定まで数十分かかる
- 利用者は夜間ベッドにおり、通知に反応して起きる運用を望まない

**買い注文と同時に、利確の指値と損切りの逆指値をSBIに入れる。**
以降はSBI側が24時間監視し、条件到達時に自動執行する。

これにより以下が同時に解決する。

- 撤退条件が「記録しただけの飾り」にならず、実際に執行される
- 自作の監視スクリプトが不要になる
- 常時稼働のサーバーが不要になる（電気代ゼロ）
- 利用者は寝ていられる

### 3.2 分析は利用者のトリガーで起動する

定期実行を主軸にしない。**PWAのボタンを押した時に分析が走る。**
想定タイミングは各市場の開場前後。

- 開場前にトリガーする限り、20分のデータ遅延は問題にならない
- トークン消費が1日1〜2回に収まる

**トレードオフ**: ザラ場中に新しい買い機会が生まれても、次にトリガーを
押すまで気づかない。売り側は3.1で担保されているため、失うのは買い機会のみ。
これは許容する。

### 3.3 すべてクラウドで動かす。ローカルの常駐は置かない

一般的なデスクトップPCを24時間起動すると、電気代が**年約13,600円**
（50W想定、31円/kWh）かかる。実際の稼働は1日数分であり、明確な無駄である。

**常駐サーバーを持たない構成にする。** 3.1で監視が不要になり、3.2で
定期実行が不要になったため、これが可能になった。

### 3.4 重い処理と軽い処理を分ける

| 処理 | 場所 | 理由 |
|---|---|---|
| 分析（数分かかる） | **GitHub Actions** | Pythonとyfinanceがそのまま使える。1ジョブ6時間で時間制限を気にしない |
| 画面表示・受付（一瞬） | **Cloudflare Pages Functions** | 秘密情報を保持し、GitHubを起動する |

Cloudflare Workers上でPythonは動くが、Pyodideの制約でyfinanceが使えない。
**株価取得はこのシステムで最も壊れやすい部分であり、そのメンテナンスを
yfinanceのコミュニティに委ねる価値が高い**ため、分析はGitHub Actionsに置く。

### 3.5 決定的な処理とAI判断を分離する

株価取得・記録の更新・通知送信は決定的な処理が行う。AIにやらせると
日によって挙動が変わり、記録の信頼性が失われる。**判断がぶれるのは許容するが、
記録がぶれるのは許容しない。**

## 4. フェーズ設計

### Phase 1: 仮想資金

- 仮想資金でシミュレーション。実際の発注は行わない
- PWAと記録フローは最初から実装する（運用体験を金銭リスクなしに検証するため）
- 最低20営業日運用する

### Phase 2: 実弾 + 手動発注

移行条件（第11章）を満たしてから移行する。変更点は2箇所のみ。

1. 提案にSBIで実際に打つ注文内容（買い・利確・損切り）が載る
2. 利用者が手動発注し、PWAの入力欄で約定を記録する

## 5. 全体構成

```
📱 スマホのホーム画面「投資」アイコン（PWA）
      │
      ▼
☁️ Cloudflare Pages
   ・PWA本体（静的ファイル）
   ・Cloudflare Access で保護（利用者のGoogleアカウントのみ）
   ・Pages Functions が秘密情報を保持し、以下を仲介する
        GET  /api/state    現在の保有・損益・提案を返す
        POST /api/analyze  分析を起動する
        POST /api/record   約定を記録する
      │
      ▼
☁️ GitHub Actions（workflow_dispatch で起動）
   ・株価・為替・ベンチマークを取得（Python + yfinance）
   ・ニュース・決算を検索（知識カットオフ対策）
   ・Claude API で判断
   ・予算とリスク許容から数量を逆算
   ・記録を Neon に保存（トランザクション）
   ・judgment を journal/ に書いてコミット
      │
      ▼
📱 Web Push で通知（保険として Discord Webhook にも並行送信）
   → PWAを開く → SBIアプリで発注 → PWAで約定を記録
```

**常駐プロセスなし。管理するサービスは Cloudflare と GitHub の2つ。**

## 6. 記録の保存先

**構造化データは Neon（Postgres）に、判断の文章は Git のファイルに置く。**
データの性質によって置き場所を分ける。

| データ | 置き場所 | 理由 |
|---|---|---|
| 取引・保有・現金・予算・提案 | **Neon（Postgres）** | 整合性、トランザクション、集計 |
| 判断の文章（journal） | **Gitのファイル（Markdown）** | 履歴に意味がある。人間が読む |
| 日次スナップショット | **Gitのファイル（JSON）** | 監査ログとバックアップ |

### 6.1 なぜデータベースが必要か（トランザクション）

約定を1件記録するには、3つの更新が同時に必要になる。

```
「NVDA 3株を $178.85 で買った」を記録する
  ① trades に1件追加
  ② cash から $536.55 を引く
  ③ positions に NVDA 3株 を追加
```

ファイル方式では**①だけ成功して②③が失敗する状態が起こり得る**。
ネットワーク断、ジョブの中断、同時実行のいずれでも発生する。
結果は「買った記録はあるのに現金が減っていない」であり、
会計データとして致命的である。

データベースなら3つまとめて成功するか、まとめて失敗するかのどちらかで、
中途半端な状態が存在しない。

**3.5で「記録がぶれるのは許容しない」と定めた以上、ここは譲れない。**

### 6.2 ファイル方式との比較

| | ファイル | データベース |
|---|---|---|
| トランザクション | ❌ なし | ✅ あり |
| 同時実行 | ❌ 後勝ちで前が消える | ✅ 制御される |
| 部分更新 | ❌ 全体を読んで全体を書く | ✅ 必要な行だけ |
| 型・制約のチェック | ❌ なし | ✅ あり |
| 集計・絞り込み | ❌ 全件読み込み | ✅ SQLで一発 |
| 書き込み速度 | ❌ 毎回コミットとプッシュ | ✅ 一瞬 |

### 6.3 なぜ D1 ではなく Neon か

分析処理は GitHub Actions 上の Python である。Neonは標準のPostgresなので
`psycopg` でそのまま接続できる。D1はCloudflare Workers外からはHTTPで
SQLを送る形になり、トランザクションの扱いも弱い。

加えてNeonの**ブランチ機能**により、Phase 1（仮想資金）と Phase 2（実弾）の
データを分離できる。両者が混ざると検証が無意味になるため、この分離は重要である。

### 6.4 監査ログとバックアップ

「Gitの履歴が監査ログになる」という利点は、以下の方法で回収する。

**毎日1回、データベースの内容をJSONに書き出してGitにコミットする。**

```
毎朝の答え合わせの処理内で
  Neon から全データを読み出す
    → data/snapshots/YYYY-MM-DD.json に保存
    → Git にコミット
```

これにより、日々の読み書きの整合性はNeonが守り、日次の記録はGitに残る。
過去のある時点の状態を復元でき、改ざんの検出にも使える。
テキスト形式のためリポジトリはほとんど膨らまない。

## 7. データ構造

### Neon（Postgres）

```sql
trades      -- 約定履歴: 日時, 銘柄, 売買, 数量, 単価, 通貨, 手数料
positions   -- 保有: 銘柄, 数量, 平均取得単価, 通貨, 利確価格, 損切り価格
cash        -- 現金残高: 通貨ごと (JPY, USD)
prices      -- 日次の終値・高値・安値（ベンチマークETFも同じ表）
proposals   -- 提案: 日時, 銘柄, アクション, 数量, 買値, 利確, 損切り,
            --       根拠, 確信度, 採用/見送り, journalへのパス
budget      -- 予算設定と消化率
```

`trades` は**追記のみ**とし、UPDATE / DELETE を行わない。それ自体が履歴になる。
`positions` と `cash` は `trades` から再計算できる状態を保つ。

### Gitのファイル

```
journal/YYYY-MM-DD.md          判断と振り返りの文章
data/snapshots/YYYY-MM-DD.json 日次スナップショット（監査ログ・バックアップ）
```

### 判断時の必須項目

以下を省略した提案は生成しない。

- 根拠
- 想定シナリオ
- **利確価格と損切り価格**（SBIに実際に打つ値。省略不可）
- 確信度

**損切り価格を決められない提案は出さない。**

### 為替の扱い

米国株はUSDのまま記録し、評価時にUSDJPYで円換算する。損益は必ず
株価要因と為替要因に分解する。

```
AAPL  +12,400円
  ├─ 株価要因 +15,100円 (+5.4%)
  └─ 為替要因  -2,700円 (USDJPY 149.1 → 148.3)
```

分解しないと、銘柄選定が良かったのか円安に助けられただけかが判別できない。

### ベンチマーク

同額をTOPIX連動ETFとS&P500 ETFに投じて放置した場合の成績を常に併記する。
実装はETFの終値を2本取得するだけ。比較対象がなければ自分の成績の
良し悪しを判断できない。

## 8. 予算管理とポジションサイジング

単なる収支記録ではなく、**予算からポジションサイズを逆算する**。

### 設定する上限

| 項目 | 役割 |
|---|---|
| 総予算 | 投資に回す上限額 |
| 1銘柄あたりの比率上限 | 一点集中を防ぐ |
| 同時保有銘柄数の上限 | 管理不能になるのを防ぐ |
| 現金比率の下限 | 買い余力を残す |
| 1取引あたりの損失許容額 | **数量の決定に使う** |

### 数量の逆算

```
株価 $178、損切り $168 → 1株あたりの想定損失 $10
1取引の損失許容が総予算の2%（¥20,000 ≒ $135）
→ 買える数量は 13株が上限
```

損切りが近い（＝確信度が高い）銘柄ほど多く買え、遠い銘柄は少なくなる。
これが「予算の見合いでリスクを分散する」の実装である。

**上限に触れる提案は通知しない。** 数量が自動調整されるか、提案自体を出さない。

```
│  保有                           │
│  NVDA  3株   +5.4%             │
│  7203  100株 -1.2%             │
└────────────────────────────┘
```

**発注に必要な情報（銘柄・数量・3つの注文）を最上部にまとめ、
SBIアプリに打ち込む順に並べる。** 誤発注を防ぐため。

### 9.2 約定の記録

`[約定を記録]` を押すと入力欄が開く。**提案した数量と価格がすでに
入っている**ため、実際の約定値と違う箇所だけ直して送信する。

HTMLの入力欄を使うため、数値入力・プルダウン・入力チェックを自由に作れる。
**スマホだけで完結し、PC操作を必要としない。**

### 9.3 通知

**動くべき時以外は通知しない。** 定期サマリーは送らない。

- 分析が完了し、**提案がある場合のみ**通知する
- 提案がない場合は通知せず、PWAを開いた時に「動きなし」と表示する
- 毎朝の答え合わせは、**確認が必要な場合のみ**通知する

送信先は Web Push。**運用開始から数週間は Discord Webhook にも並行送信する**
（iOSのWeb Pushが確実に届くかを検証するまでの保険）。安定を確認したら外す。

### 9.4 毎朝の答え合わせ

毎朝、GitHub Actions の定期実行で前日の約定を確定させる。

**前提となる制約**: SBI証券の約定通知メールは**国内株式のみ**で、
**米国株は非対応**。メールに依存しない方式を採る。

**推定ロジック**: 前日の日足の高値・安値を取得し、`positions.json` の
利確価格・損切り価格と突き合わせる。

- 前日の**安値** <= 損切り価格 → 損切り注文が成立した可能性
- 前日の**高値** >= 利確価格 → 利確注文が成立した可能性

該当があれば通知し、PWAで確認ボタンを出す。該当がなければ通知しない。
ほとんどの日は通知が来ない。

`[売れた]` を押すと**推定した約定価格がプリフィルされた入力欄**が開く。
合っていればそのまま送信する。

### 9.5 CSVによる突合（月1回推奨）

**SBI証券には参照系のAPIが存在しない。** 残高・保有・約定履歴を
プログラムから取得する手段がないため、**システムの記録の根拠は
利用者が入力した内容だけ**になる。

したがって以下が起こり得る。

- 約定の記録を忘れる → 保有していない銘柄を保有していることになる
- 価格を打ち間違える → 損益がずれたまま固定される
- 手数料が反映されない → 実際より成績が良く見える

**そしてシステムは、このズレに自力で気づけない。**

本システムの目的は測定である。**記録が現実とずれた時点で、
測定値もベンチマーク比較も振り返りも、すべて無意味になる。**
したがってCSVによる突合は任意ではなく、**月1回の実施を推奨する**。

**突合の処理**: SBIからダウンロードした約定履歴CSVを取り込み、
システムの記録との差分を表示する。

```
📋 突合結果 2026-10-01

  ✅ NVDA   一致
  ⚠️ 7203   数量が違います
            システム 100株 / 実際 200株
            → 9/18の買い増しが記録されていない可能性
  ⚠️ 現金    ¥12,300 の差
            → 手数料の未反映

  [システムの記録を実際に合わせる]
```

差分を自動で適用せず、**必ず利用者に提示してから反映する**。
自動で上書きすると、どこでズレたのかを学ぶ機会が失われる。

**CSVのダウンロードはPC操作が必要**（スマホからはできない）。
毎日の運用はスマホだけで完結するが、月1回だけPCでの作業が発生する。

## 10. 秘密情報の管理

**価値の高い秘密ほど、露出しにくい場所に置く。**

| 置き場所 | 何を置くか | 保護 |
|---|---|---|
| **GitHub Secrets** | Claude APIキー、**Neonの接続情報**、Web Push秘密鍵、Discord Webhook URL | 暗号化保存。ログにも出ない |
| **Cloudflare Pages の環境変数** | GitHub Actions を起動するトークン、**Neonの読み取り用接続情報** | サーバー側。PWAからは見えない |
| **PWA（ブラウザ）** | **何も置かない** | — |

**PWAはブラウザで動くためコードが公開される。秘密情報を一切持たせない。**
GitHubトークンやAPIキーが必要な操作はすべて Pages Functions が代行する。

GitHubトークンは **Fine-grained personal access token** を使い、権限を
「このリポジトリのワークフローを起動する」だけに絞る。有効期限も設定する。

### 認証

Cloudflare Access で PWA を保護し、利用者のGoogleアカウントのみが
アクセスできるようにする。URLが漏れても取引記録は見られない。

## 11. Phase 2 への移行条件

**Phase 1が検証するのは「システムが動くこと」であり、「戦略が勝てること」ではない。**
両者は必要なサンプル数が桁違いに異なるため、条件を分けて定める。

### 11.1 実弾に移る条件（システムの検証）

全て満たすこと。

1. **20営業日以上**運用した
2. ベンチマーク（TOPIX / S&P500）との比較が出せている
3. 提案画面が実用に耐える（読んでそのままSBIに打てる状態）
4. 想定外のクラッシュ・データ欠損が直近10営業日でゼロ
5. **journalを読み返して、自分の判断の癖を1つ以上言語化できている**

5番目が本質的な条件である。これが書けない場合、実弾に移す準備ができていない。

### 11.2 戦略を評価できる条件（別軸）

**20営業日で貯まるトレードは約10件であり、勝率の判定には全く足りない**（16.2参照）。

| トレード数 | 勝率の95%信頼区間 |
|---|---|
| 10件 | ±30%（判断不能） |
| 30件 | ±17% |
| 100件 | ±9% |

したがって「このルールは勝てる／勝てない」の判定は、**トレード数が30件を超えてから**
行う。20営業日という日数条件とは独立に管理する。

**実弾に移ることと、戦略が検証されたことは別である。** 実弾に移る時点では、
戦略の優劣はまだ分かっていない。ポジションサイズを控えめに始める理由がここにある。

## 12. 安全装置

- **dry-run**: 通知を送らず標準出力に出すモード。開発時の既定値
- **上限超過の提案を出さない**: 予算・比率・保有数の上限に触れる提案は生成しない
- **損切り価格のない提案を出さない**
- **取得失敗時のスキップ**: yfinanceが失敗した日は欠測として記録し、判断を行わない。古い価格で判断させない
- **Phase 1では仮想資金であることを画面に明示する**
- GitHub Actions の無料枠超過時は自動停止（課金事故が起きない設定）
- **突合の差分は自動適用しない**。必ず利用者に提示してから反映する

## 13. テスト方針

TDDで実装する。yfinanceと通知はモックする。

重点箇所。

- `portfolio.py`: 買→売の損益計算、**特に通貨をまたぐケース**
- `sizing.py`: 損切り価格からの数量逆算、**上限に触れる境界値**
- `market.py`: 銘柄シンボルの正規化（`7203` → `7203.T`）
- 毎朝の答え合わせ: 高値・安値と利確・損切り価格の**境界値**（等しい場合に発火するか）
- `db.py`: **約定記録のトランザクション**。途中で失敗させて、部分的に書かれていないことを確認する

## 15. 判断ロジック

### 15.1 役割分担

**利用者が「何を根拠に買うか」の基準を決め、AIはその基準に必要な情報を集め、
一貫して当てはめ、判断を記録する。**

| AIが得意 | AIが苦手 |
|---|---|
| 決算・ニュース・開示を読んで要約する | 価格の予測 |
| 決めた基準を感情なしに一貫して適用する | 相場の空気を読む |
| 過去の判断を読み返して癖を指摘する | タイミング |

AIに丸投げすると、勝っても負けても理由が分からない。基準を明示することで、
**基準が悪かったのか、適用がまずかったのか、運だったのかを切り分けられる**。

### 15.2 2段階構成

```
① Python が全銘柄を機械的にふるいにかける
        ↓ 数十銘柄
② AI がその中から決算・ニュースを読んで判断する
```

**①を機械にやらせる理由**: AIに「日本株から選んで」と指示すると、
**知っている有名企業しか出てこない**。参考動画でAIが選んだのは
ファーストリテイリング、東京エレクトロン、三菱UFJ、トヨタ、キーエンスの
5社で、**すべて日経225の超大型株**だった。これは銘柄を選んでいるのではなく
名前を思い出しているだけである。

2段階に分けることで、成績が悪かった時に**どちらの段階が原因かを切り分けられる**。

### 15.3 採用する売買ルール（v1）

**William O'Neil（CAN SLIM）型を出発点とする。**

| | 値 |
|---|---|
| 損切り | **-8%** |
| 利確 | **+20〜25%** |
| リスクリワード比 | 約3:1 |
| **必要勝率** | **24〜29%** |

**出典の比較**（同じ「8%ルール」でも中身が違う）

| 提唱者 | 損切り | 利確 | 必要勝率 | 根拠 |
|---|---|---|---|---|
| **William O'Neil** | -7〜8% | **+20〜25%** | **24〜29%** | IBDによる勝ち銘柄の大規模調査 |
| 熊谷亮（2015） | -8% | +8% | **50%** | 8%の理論的根拠は明記なし |
| PAN | -15% | 記載なし | — | 「O'Neilの8%は時代遅れ」自身の経験 |

**O'Neil型を選ぶ理由は必要勝率である。** 同じ-8%損切りでも、利確を+8%にすると
必要勝率が50%に跳ね上がる。短期売買で勝率50%超を安定して出すのは難しい。

なお参考動画の「プラス8%ルールのようなもの」は熊谷型と考えられるが、
**動画内で根拠は語られていない**。

### 15.4 必要勝率を毎回表示する

提案のたびに、そのトレードが期待値プラスになるために必要な勝率を計算して表示する。

```
必要勝率 = 損切り幅 / (利確幅 + 損切り幅)
```

米国株は手数料（往復1%）を織り込む（利確幅 -1%、損切り幅 +1%）。

**これにより、提案を見た瞬間にそのトレードがどれだけ無理をしているかが分かる。**
また、実測の勝率と必要勝率を比較すれば、ルールが機能しているかが判定できる。

### 15.5 期間ではなく値幅で市場を制約する

**保有期間は銘柄ごと・状況ごとに判断する。期間で機械的に区切らない。**
「中長期は不透明だが今週は上昇基調」という銘柄に短期で乗ることを許容する。

制約は手数料から導かれるもの1つだけ。

| 狙う値幅 | 日本株（手数料0円） | 米国株（往復1%） |
|---|---|---|
| +2% | ✅ | ❌ 半分が手数料に消える |
| +3% | ✅ | ⚠️ 1/3が消える |
| +5% | ✅ | ⚠️ 許容範囲 |
| +10%以上 | ✅ | ✅ |

**「+5%未満を狙う短期は日本株限定」。** 米国株でも+10%狙いなら短期でよい。

### 15.6 戦略タグと確信度

各提案に**狙いのラベル（戦略タグ）**と**確信度**を付けて記録する。

複数の狙い方を混ぜると、どれが効いていたか分からなくなる。タグを付ければ
**戦略別に勝率と期待値を集計できる**。

```
📊 戦略別の成績

  短期モメンタム   12件  勝率 42%  期待値 +3.1%
  決算後の反応      5件  勝率 20%  期待値 -1.8%
  中長期ファンダ    3件  勝率 67%  期待値 +6.2%
```

確信度も同様に集計し、**「確信度が高いトレードは実際に勝率が高いのか」**を測る。
ここが当てにならなければ、確信度で比重を変えてはならない、という結論になる。

**実測が出るまで、比重（ポジションサイズ）は揃える。** 根拠のない傾斜をかけない。

### 15.7 AI自身による振り返り

各判断のあとに、AI自身が「前回の判断はどうだったか、何を見落としたか」を
journal に書く。参考動画にあった仕組みを踏襲する。

### 15.8 スクリーニング条件（v1）

15.2 の①「Pythonによる機械的な絞り込み」の具体条件。

| | 条件 | 意図 |
|---|---|---|
| 1 | **時価総額 300億円以下** | 株価の身軽さ（小型株） |
| 2 | **売上高増減率 20%以上** | 成長の速度 |
| 3 | **売上高営業利益率 10%以上** | ビジネスの独自性 |
| 4 | **ROE 15%以上** | 経営効率 |
| 5 | **自己資本比率 40%以上** | 財務基盤 |

**出典**: Instagram投稿（hide._money / 日本株歴40年、2026-07-29）

**採用理由**: この5条件は **CAN SLIM とほぼ一致する**。

| 観点 | この基準 | O'Neil (CAN SLIM) |
|---|---|---|
| 成長性 | 売上高 +20%以上 | C/A: EPS成長 +25%以上 |
| 収益性 | 営業利益率10%、ROE 15%以上 | A: ROE 17%以上 |
| 規模 | 時価総額300億円以下 | S: 発行株数の少ない銘柄を好む |
| 過去の値動き | 「爆騰のDNA」 | L: 同業種内での相対力 |
| 財務 | 自己資本比率 40%以上 | （明示的な基準なし） |

**独立した2つの出典がほぼ同じ結論に到達している**ことを、採用の根拠とする。
発信源の表現（「億り人」等）ではなく、条件が数値で検証可能であることを重視する。
効かなければ16章のバージョン管理の手順で外す。

**資金規模との整合**: 時価総額300億円以下は小型株であり、通常は流動性が
懸念材料になる。ただし本プロジェクトの資金は55万円であり、**この規模では
流動性の制約を受けない**。基準と資金規模が噛み合っている。

### 15.9 スクリーニングの実装方式

**yfinance で日本株のファンダメンタルズが取得できることを実測で確認した**
（2026-09-07）。

| 項目 | 取得元 |
|---|---|
| 時価総額 | `info["marketCap"]` |
| 売上高増減率 | `info["revenueGrowth"]` |
| 営業利益率 | `info["operatingMargins"]` |
| ROE | `info["returnOnEquity"]` |
| 自己資本比率 | `balance_sheet` の Stockholders Equity ÷ Total Assets |

**実測サンプル**

```
7203 トヨタ        時価総額 36.6兆円  売上成長 +10.4%  営業利益率  7.9%  ROE 12.4%
6920 レーザーテック 時価総額 3.19兆円  売上成長 -26.3%  営業利益率 44.4%  ROE 33.9%
3993 PKSHA        時価総額  983億円  売上成長 +81.1%  営業利益率 13.8%  ROE  7.7%
                                                        自己資本比率 63.4%
```

3銘柄とも5条件を通過しない（時価総額で脱落）。フィルタは機能している。

**性能の制約**: 取得は **1銘柄あたり約0.75秒**。全4,000銘柄で**約50分**かかる。
毎回の分析で実行するのは非現実的である。

**対処**: 財務データは四半期に一度しか更新されないため、**週1回のバッチで
全銘柄を取得し Neon に保存する**。日々の分析では Neon から SQL で条件に
合う銘柄を抽出する（1秒未満）。

```
【週1回・GitHub Actions cron】約50分
   全銘柄のファンダメンタルズを取得 → Neon に保存

【毎日・トリガー時】1秒未満
   Neon から条件に合う銘柄を SQL で抽出 → AI が詳しく見る
```

GitHub Actions の消費は週50分＝**月約215分**。分析分と合わせて月400分程度で、
無料枠2,000分の約20%にとどまる。

**銘柄リストの取得元**: JPXが公開する上場銘柄一覧を使う（実装時に確認）。

## 16. ルールのバージョン管理

**ロジックは運用しながら変更していく。** そのため変更を管理する仕組みを設計に入れる。

### 16.1 バージョンとして記録する

```
rules/
├── v1.md    O'Neil型 -8%/+22%   採用 2026-09-08
├── v2.md    利確を+15%に変更     採用 2026-10-15
│            理由: <出典URL>
│            v1の成績: 32件 勝率34% 期待値+2.1%
└── ...
```

各提案・トレードに `rule_version` を記録する。これにより**バージョン別の成績を
比較でき、変更が改善だったか改悪だったかが判定できる**。

変更時は**理由と出典を必ず記録する**。出典のない変更は記録しない。

### 16.2 サンプル数のガード

**勝率の推定には十分なトレード数が要る。**

| トレード数 | 勝率の95%信頼区間 |
|---|---|
| 10件 | ±30%（判断不能） |
| 30件 | ±17% |
| 50件 | ±13% |
| 100件 | ±9% |

年125トレードのペースでは、**20営業日で貯まるのは約10件**にすぎない。

**10件の成績が悪いことを理由にルールを変えると、次の10件でも同じことが起きる。**
負ける→ルールを変える→また負ける→また変える、は投資で最も典型的な失敗である。

したがって、**現行バージョンのサンプルが30件未満での変更には警告を表示する**。
変更を禁止はしない。「まだN件です。この判断は運の可能性が高いです」と表示し、
判断は利用者に委ねる。

### 16.3 仮想フェーズでの並走

**Phase 1（仮想資金）では、複数のルールバージョンを同時に走らせられる。**
新旧のルールを同じ銘柄・同じ相場環境に並行適用し、成績を直接比較する。

**実弾ではできない検証であり、Phase 1を仮想資金とすることの最大の利点である。**

### 16.4 外部情報の取り込み手順

利用者が投資家のYouTube動画などを参考にしたい場合の手順。

**AIは動画を直接視聴できない。** ただし NotebookLM 経由なら内容を読み取れる
（本プロジェクトで実証済み）。

```
利用者: 動画を NotebookLM に取り込み、URLを共有する
AI:     Chrome経由で NotebookLM を読み、内容を抽出する
        → ルールの出典として記録し、既存ルールと数値で比較する
```

**取り込む際は、必ず必要勝率に換算して既存ルールと比較する。**
提唱者の知名度ではなく数字で判断する。

## 18. セキュリティ

### 18.1 想定するリスク

| リスク | 深刻度 | 理由 |
|---|---|---|
| **APIキー・トークンの誤コミット** | **高** | Claude APIの不正利用、GitHubリポジトリの操作 |
| 依存パッケージの脆弱性 | 中 | yfinance等の外部ライブラリ経由 |
| コードの脆弱性（XSS等） | 低 | 単一利用者。外部からの入力は株価データとAIの応答のみ |
| 金銭被害 | **なし** | **発注機能を持たないため、資金は動かせない** |

**最大のリスクは秘密情報の漏洩である。** ここに対策を集中させる。

### 18.2 GitHub CodeQL を採用しない理由

CodeQLおよびSecret Protectionは、**非公開リポジトリでは有料**である。

- Code Security（CodeQL）: $30 / active committer / 月
- Secret Protection: $19 / active committer / 月

本システムの実費はClaude APIの月$3〜10であり、**費用が釣り合わない**。
リポジトリを公開すれば無料になるが、取引記録が公開されるため採れない。

また、CodeQLが得意とするのは上表の「低」に該当する領域であり、
**最大のリスクである秘密情報の漏洩には、無料ツールのほうが有効**である。

### 18.3 採用する対策（すべて無料）

| 対策 | 役割 | 実行場所 |
|---|---|---|
| **pre-commitフック（gitleaks）** | **コミット前に手元で止める** | ローカル |
| **gitleaks / Betterleaks** | 秘密情報の混入を検査 | GitHub Actions |
| **Dependabot** | 依存パッケージの脆弱性を通知（非公開リポジトリでも無料） | GitHub |
| **bandit** | Pythonの危険なパターンを検出 | GitHub Actions |
| `.gitignore` | 秘密ファイル・取引記録の一部を対象外にする | ローカル |

**pre-commitフックを最重要とする。** CodeQLやGitHubの検査は「コミット後に
見つける」ものだが、pre-commitは「そもそも上げさせない」。秘密情報は
一度でもリモートに到達したら漏洩したものとして扱う必要があるため、
手前で止めるほうが本質的に強い。

### 18.4 秘密情報を漏らしてしまった場合の手順

**優先順位を守ること。** 履歴から消すのは二の次である。

1. **該当のトークン・キーを即座に無効化する**（GitHub、Anthropic、Cloudflareの管理画面）
2. 新しいトークンを発行し、GitHub Secrets / Cloudflare の環境変数を更新する
3. 動作確認する
4. （任意）Git履歴から削除する

**1を飛ばして4をやってはならない。** 履歴を書き換えている間も、漏れた
トークンは有効なままである。

| 為替（円↔ドル） | 0銭 |

### 19.4 米国株の手数料が判断ロジックに与える制約

米国株は買いと売りで手数料が2回かかるため、**往復で約1%**を要する。

```
$535 で買う → 手数料 $2.65
$580 で売る → 手数料 $2.87
                合計 $5.52
```

**株価が1%上昇しただけでは、手数料で利益が消える。**

したがって、**米国株の利確ラインは最低でも +2〜3% 以上に設定しなければ
意味を持たない**。日本株は手数料が0円のためこの制約を受けない。

**判断ロジックを設計する際の必須の入力条件とする。** また、Phase 1の
仮想資金でも手数料をシミュレートしなければ、実弾との乖離要因になる。
