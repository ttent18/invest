## 1. なぜ作るのか

**「買った」を記録する経路が、いまどこにも存在しない。**

```
提案がデータベースに入る   ✅ 動いている
      ↓
利用者がSBIで買う         📱 手作業
      ↓
買ったことを記録する       ❌ 経路が無い
      ↓
毎朝の答え合わせ           ❌ 保有が空なので何も見ない
      ↓
勝率が溜まる               ❌ 永久に0件
```

計画1で作った「じっくり枠 vs 回転枠のどちらが向いているかを実測する」仕組みは、
**記録が始まらない限り一生データが溜まらない。** 期限10営業日の判定も、
保有が空なので動かない。総資金も初期値のまま増えない。

つまりこのPWAは「スマホで見られると便利」ではなく、**輪を閉じる最後の一片**である。

### 用語

この設計で出てくる、投資と関係のない言葉を先に説明しておく。

| 言葉 | 意味 |
|---|---|
| **PWA** | ふつうのWebページだが、スマホのホーム画面にアイコンとして置け、アプリのように開けるもの。アプリストアを通さない |
| **Cloudflare Pages** | HTMLやJavaScriptを置いて公開する場所。無料 |
| **Pages Functions** | 上と同じ場所で動く小さなプログラム。**パスワードなどの秘密情報を持てる**のが要点 |
| **Cloudflare Access** | 「このページは自分のGoogleアカウントでしか開けない」という鍵。無料 |
| **Web Push** | Webページからスマホに通知を送る仕組み。アプリストア不要 |
| **VAPID** | 「この通知は確かに自分のサーバーが送った」と証明するための鍵。自分で作る |

## 2. 何を作るか（範囲）

### 作るもの

1. スマホで**見る**（今日やること・保有・収支）
2. スマホで**記録する**（買った・売った）
3. スマホから**起動する**（いま分析して）
4. スマホに**通知する**（動くべきときだけ）

### 作らないもの

- **発注機能。** SBIには発注APIが無い（親設計 第2章）。発注は利用者がSBIのアプリで行う
- **株価のリアルタイム表示。** 取得元が15〜20分遅れなので、遅れた値をそれらしく見せない
- **AIとの対話画面。** 深掘りはMacのClaude Codeで行う（親設計 第5章）
- **複数人での利用。** 利用者は1人

## 3. 全体の流れ

```
📱 iPhoneのホーム画面「投資」アイコン
      │
      ▼
☁️ Cloudflare Pages（*.pages.dev）
   ・画面本体（HTML / JavaScript）
   ・Cloudflare Access で保護（利用者のGoogleアカウントのみ）
   ・Pages Functions が秘密情報を持ち、以下を仲介する
        GET  /api/state      いまの状態を返す
        POST /api/fills      「買った/売った」を1行そのまま保存する
        POST /api/analyze    分析を起動する
        POST /api/subscribe  通知の宛先を登録する
      │
      ▼
🗄️ Neon（PostgreSQL）
      ▲
      │
☁️ GitHub Actions（Python）
   ・記録の反映（fills → trades / positions / cash）
   ・スクリーニング・分析・朝の確認（計画1で実装済み）
   ・通知の送信
      │
      ▼
📱 Web Push で通知
```

**常駐するサーバーは無い。** 管理するのは Cloudflare と GitHub と Neon の3つ。

## 4. 記録の仕組み — 計算をどこでやるか

### 決定: Cloudflare側は計算しない。Pythonだけが計算する

```
スマホで「買った」を押す
      ↓
Pages Functions が、言われた内容を fills テーブルに1行入れるだけ   ← 計算しない
      ↓
GitHub Actions の Python が未反映の fills を読み、
trades / positions / cash に反映する                              ← 計算はここだけ
```

### なぜこうするか

保有株数の更新や平均取得単価の計算を Cloudflare側（JavaScript）に書くと、
**同じ計算がPythonとJavaScriptの2箇所に存在する**ことになる。

2026-09-07 の開発で見つかった欠陥の多くは、この形だった。

- 枠の名前が、コードとデータベースの制約の2箇所にあった
- ルールの利確・損切り幅が、コードとJSONファイルの2箇所にあった
  （しかもAIが書き換えられる側を見ていた）
- マイグレーションを実行する経路が、テストにしか無かった

**同じ罠を新品で作らない。**

副産物として、**利用者が「こう買った」と申告した内容が、計算結果とは別に生のまま残る。**
あとで数字が合わないときに、申告が違うのか計算が違うのかを切り分けられる。

### 反映までの時間

反映は GitHub Actions が走ってから。**約1分**かかる。

画面は「記録しました（反映待ち）」を即座に出し、反映後に保有へ反映される。
実弾ではなく検証で回している段階では、この1分は問題にならないと判断した。
気になるようになったら、反映専用の軽いワークフローを別に切る。

### 反映に失敗したら

**黙って消さない。** `fills.apply_error` に理由を書き、`applied_at` は NULL のまま残す。
画面には「反映できていない記録が N 件あります」と出す。

反映が失敗する例: 保有していない銘柄を売ったことにした、保有株数を超えて売った、
現金が足りない。いずれも利用者の入力ミスなので、気づける形にする。

## 5. 画面

### 5.1 今日やること（トップ）

**出すもの**

- 未実行の提案（`proposals.outcome = 'pending'`）
- 各提案について: 銘柄コード・会社名・**枠**・株数・買値・**損切り**・**利確**・投資額
- 「なぜ買うのか」（`rationale` の要約）。全文は開いて読める
- 反映できていない記録があれば、その警告

**押せるもの**

- **[ 買った ]** … 株数と価格が提案の値で埋まった入力欄が開く。
  実際の約定価格だけ直して確定する
- **[ 見送る ]** … `proposals.outcome = 'skipped'` にする。理由も一言残せる
- **[ いま分析して ]** … GitHub Actions を起動する

**設計上の注意**

損切り価格を**いちばん目立たせる**。この仕組みの安全装置はSBI側の逆指値であり、
それを入れ忘れると全部が崩れる。「SBIで逆指値を入れましたか」の確認を
記録の確定時に必ず挟む。

### 5.2 保有

**出すもの**

- 銘柄・枠・株数・平均取得単価・現在値・含み損益（金額と率）
- 損切り価格・利確価格までの距離
- **回転枠の期限**（何営業日経過 / 期限10営業日）。過ぎているものは赤く出す

**押せるもの**

- **[ 売った ]** … 株数と価格を入れて確定する

**現在値について**

15〜20分遅れの値である。**「遅れている」と画面に明記する。**
リアルタイムに見せかけると、その値を根拠に判断してしまう。

### 5.3 収支

**出すもの**

- 現金・評価額・合計・初期資金からの増減
- 確定した損益の累計
- **枠ごとの成績**（これがこの画面の主目的）

```
              じっくり枠    回転枠
  決着した数      4件         9件
  勝ち            2件         3件
  勝率           50.0%       33.3%
  損益トントン   26.7%       33.3%    ← これを上回っているか
  平均保有日数    31日         9日
  期限切れ         —          2件
  合計損益     +38,400円   -2,100円
```

**決着が15件ずつ溜まるまで、この数字で配分を変えない**（rules/v3.md）。
画面にもその旨を出し、少ないうちは「まだ判断できる件数ではありません」と表示する。

## 6. 通知

### 6.1 iPhone の絶対条件

**ホーム画面に追加したアイコンから開いた場合のみ、通知が届く。**
Safariのタブで開いているだけでは届かない（iOS 16.4以降、Appleの仕様）。

出典: [PWA iOS Limitations and Safari Support (2026)](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)

セットアップ手順に「共有 → ホーム画面に追加」を必須の手順として書く。
また、**タブで開かれていることを検知したら画面上部に案内を出す**
（`window.navigator.standalone` で判定できる）。

### 6.2 いつ通知するか

利用者の要望は「**動くべきとき以外は通知いらない**」。

| 通知する | 通知しない |
|---|---|
| 買うべき提案が出た（1件以上） | 提案が0件だった |
| 損切り・利確に到達した可能性がある | 何も起きていない朝 |
| 回転枠の期限が切れた | 分析が終わっただけ |
| 記録の反映に失敗した | スクリーニングが終わった |

**通知は「あなたが動く必要がある」という意味だけを持たせる。**
それ以外を送ると、通知が意味を失う。

### 6.3 どう送るか

送信は **Python（GitHub Actions）** から。`pywebpush` を使う。
Cloudflare側には送信の仕組みを置かない（秘密の鍵を2箇所に置きたくないため）。

```
GitHub Actions（分析・朝の確認の最後）
   ↓ push_subscriptions を読む
   ↓ pywebpush で送信（VAPID秘密鍵は GitHub Secrets）
Apple / Google の通知サーバー
   ↓
📱 iPhone
```

**宛先が無効になったら消す。** 通知サーバーが 404 / 410 を返したら、
その購読は失効しているので `push_subscriptions` から削除する。
残したまま送り続けると、毎回失敗が記録され続けて本当の失敗が埋もれる。

### 6.4 通知が届かなくても運用が止まらないこと

**通知はあくまで補助。** 届かなくても、アイコンを開けば同じ情報が見える。
通知の送信に失敗しても、分析や記録の処理は成功として扱う
（失敗の事実は `data_gaps` に残す）。

## 7. データベースに足すもの

### 7.1 fills — 利用者が申告した約定（生の記録）

```sql
CREATE TABLE IF NOT EXISTS fills (
    id           BIGSERIAL      PRIMARY KEY,
    recorded_at  TIMESTAMPTZ    NOT NULL DEFAULT NOW(),
    -- 買いは、どの提案に対する約定かを持つ（枠・利確・損切りをここから引くため）。
    -- 売りは提案を経由しないことがあるので NULL を許す。
    proposal_id  BIGINT         REFERENCES proposals(id),
    symbol       TEXT           NOT NULL,
    side         TEXT           NOT NULL CHECK (side IN ('buy', 'sell')),
    quantity     INTEGER        NOT NULL CHECK (quantity > 0),
    price        NUMERIC(18, 4) NOT NULL CHECK (price > 0),
    currency     TEXT           NOT NULL,
    fee          NUMERIC(18, 4) NOT NULL DEFAULT 0,
    -- 反映済みなら日時が入る。NULL は未反映。
    applied_at   TIMESTAMPTZ,
    -- 反映できなかった理由。黙って消さないために残す。
    apply_error  TEXT
);
```

**この表は追記のみ。** 一度入れた行の内容は書き換えない（`applied_at` と
`apply_error` を除く）。利用者が申告した事実そのものを保つ。

### 7.2 push_subscriptions — 通知の宛先

```sql
CREATE TABLE IF NOT EXISTS push_subscriptions (
    id            BIGSERIAL   PRIMARY KEY,
    endpoint      TEXT        NOT NULL UNIQUE,
    p256dh        TEXT        NOT NULL,
    auth          TEXT        NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_ok_at    TIMESTAMPTZ,
    failure_count INTEGER     NOT NULL DEFAULT 0
);
```

`endpoint` が宛先そのもので、端末ごとに一意。同じ端末から再登録された場合は
上書きする（`ON CONFLICT (endpoint) DO UPDATE`）。

### 7.3 trades に枠を足す

枠ごとの勝率を出すために、取引にも枠が要る。

```sql
ALTER TABLE trades ADD COLUMN IF NOT EXISTS bucket TEXT;
```

保有（`positions`）には既に `bucket` がある（v3のマイグレーション）。

## 8. API

Pages Functions が提供する。**すべて Cloudflare Access の内側**にあり、
認証済みの利用者からのリクエストしか届かない。

| メソッド | パス | すること |
|---|---|---|
| GET | `/api/state` | 提案・保有・現金・枠ごとの成績・未反映の記録をまとめて返す |
| POST | `/api/fills` | 申告された約定を `fills` に1行入れる。**計算しない** |
| POST | `/api/proposals/{id}/skip` | 提案を「見送る」にする |
| POST | `/api/analyze` | GitHub Actions の analyze を起動する |
| POST | `/api/subscribe` | 通知の宛先を `push_subscriptions` に登録する |

### 接続方法

Pages Functions からは通常のPostgres接続（TCP）が使えないため、
Neon が提供する **HTTP経由のドライバ**（`@neondatabase/serverless`）を使う。
[Neon の Cloudflare Pages 向け公式手順](https://neon.com/docs/guides/cloudflare-pages)がある。

### 書き込みは fills と push_subscriptions と proposals.outcome のみ

**Functions が触ってよい表を、この3つに限定する。**
`positions` / `cash` / `trades` は Python だけが書く。

## 9. 秘密情報の置き場所

| 秘密情報 | 置く場所 | 理由 |
|---|---|---|
| Neonの接続文字列 | Cloudflare の環境変数 ＋ GitHub Secrets | 両方から接続する |
| GitHubのトークン | Cloudflare の環境変数のみ | 分析の起動に使う |
| VAPID **秘密**鍵 | GitHub Secrets のみ | 送信はPythonだけが行う |
| VAPID **公開**鍵 | Cloudflare の環境変数（画面に出てよい） | 購読の登録に必要。公開前提の鍵 |

**画面のJavaScriptには、VAPIDの公開鍵以外の秘密を一切置かない。**
ブラウザに配られるものは全部見えると考える。

### GitHubのトークン

細かく権限を絞ったトークン（fine-grained PAT）を使う。

- 対象リポジトリ: このリポジトリのみ
- 権限: **Actions（write）のみ**。コードの読み書きは与えない
- 有効期限を必ず設定する

## 10. セットアップ手順（利用者が行う分）

順番どおりに行う。**画面を見ながら一緒に進める。**

1. **VAPIDの鍵を作る** — こちらで生成コマンドを用意する。公開鍵と秘密鍵が出る
2. **GitHub Secrets に登録** — `VAPID_PRIVATE_KEY` / `VAPID_PUBLIC_KEY` / `VAPID_SUBJECT`
3. **GitHubのトークンを作る** — 上記の権限で。有効期限を設定する
4. **Cloudflare Pages のプロジェクトを作る** — このGitHubリポジトリと繋ぐ
5. **Cloudflare に環境変数を登録** — `DATABASE_URL` / `GITHUB_TOKEN` / `VAPID_PUBLIC_KEY`
6. **Cloudflare Access を有効にする** — Pages の設定の「Access Policy」から。
   自分のGoogleアカウントだけを許可する
7. **iPhoneで開く** → **共有 → ホーム画面に追加** → アイコンから開く
8. **通知を許可する** — 画面の「通知を受け取る」ボタンを押す
   （**ホーム画面のアイコンから開いていないと出ない**）

## 12. 既知の制約

| 制約 | 内容 |
|---|---|
| 反映まで約1分 | 計算をPythonに一本化した代償。検証段階では許容する |
| 株価は15〜20分遅れ | 取得元の仕様。画面に明記する |
| ホーム画面必須 | iOSの仕様。タブで開くと通知が来ない |
| 総資金が固定値 | `config.py` に直書きされており、資金が増えても反映されない。**記録が動き出す前に直す必要がある**（計画2の実装に含める） |
| じっくり枠に期限が無い | 動かない銘柄が枠に居座る穴が残っている（rules/v3.md に明記済み） |

## 13. 計画1から持ち越す宿題

このPWAを作る前に、**総資金の直書きを直す**。

`src/investment/config.py` の `total_capital=550_000` はコードに直書きされており、
`cash` テーブルに実際の残高があるのにそちらを見ていない。記録が動き出すと
現金が変動するため、**直さないと初日から数字がずれ始め、しかも気づけない。**

いま直せば「550,000円と一致する」ことで正しさを確認できる。
資金が動き始めてからでは比較対象が無い。
